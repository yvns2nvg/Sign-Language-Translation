# kslx 결과 정리 (2026-09-04~07 세션)

`model/`(기존 TCN, 3000클래스 val 99.6%)의 검증 방식이 데이터 누수였다는 걸
증명하고, 누수 없는 프로토콜로 재학습해서 **처음으로 signer_out(미학습 수어자)
정확도를 확보**했다. 이 문서가 그 전체 과정과 최종 수치의 기록이다.

## 0. 요약

- 기존 99.6%는 모델 성능이 아니라 **분할 프로토콜의 산물**이다. 3D 키포인트가
  같은 take의 5개 카메라 앵글 파일에 비트 단위로 동일하게 복사돼 있어서,
  랜덤 분할에서는 val 샘플의 사본이 train에 그대로 들어간다.
  같은 조건(랜덤 분할, 2D 전용, 완전히 다른 모델/피처)에서도 **99.5%**가 재현됐다.
- 누수를 제거한 정직한 지표: **signer_out(미학습 수어자) top-1 97.8%**.
  이전 세션 문서는 "수어사가 1명뿐이라 이 숫자를 측정할 수 없다"고 명시했는데,
  AI Hub 세션을 16명분 전부 받으면서 처음으로 계산 가능해졌다.
- 정규화 코드에 있던 버그(어깨 동시 미검출 시 좌표가 최대 100만 배 폭발)를
  찾아 고쳤다 — 고치기 전에는 모든 프로토콜이 순수 확률(1/271) 수준에 멈춰 있었다.
- 학습에 증강(회전/전단/스케일/노이즈/손 결측/미러)을 넣어 **손 결측 시
  14%로 붕괴하던 정확도를 98.8%로, yaw 30도 회전 열화도 -23%p에서 -0.3%p로**
  고쳤다. 깨끗한 데이터에서는 0.5~1.2%p만 손해 본다.
- **최종 추천 체크포인트: `runs/signer_out_aug.pt`** (271단어, top-1 97.8%, 모든
  강건성 변형에서 1%p 이내 열화). 이 저장소에 포함돼 있다.
- 271단어를 3000단어로 넓히려다 이 PC(RAM 31GB)에서 memmap 대규모 처리
  중 **두 번 강제종료**됐다 — 원인 분석 후 메모리 안전한 배치/청크 로딩으로
  고치고, 안전 범위인 **1200단어**로 재학습했다. **signer_out top-1 98.0%**
  (271단어와 사실상 동일 — 어휘 4.4배 확장에도 정확도 안 떨어짐), 강건성도
  동급. **새 기본 추천 체크포인트: `runs/signer_out_c1200_aug.pt`**
  (동사·형용사 121개 포함, 이전엔 7개뿐이었음). §10 참고.
- 웹캠에서 단어를 이어서 하면 자동으로 문장 경계를 감지하고(`kslx/stream.py`),
  인식된 단어 나열을 `kiwipiepy` 품사 태깅 기반 규칙으로 자연스러운 한국어
  문장으로 합친다(`kslx/sentence.py`, 예: "나 학교 가다" → "나는 학교에
  가요") — 완전 오프라인, 학습 불필요. §8 참고.
- 노트북 웹캠 실측 결과 단어 인식이 좋지 않다는 피드백을 받아 조사함:
  OpenPose→MediaPipe 대체가 인식 성능을 떨어뜨리는 건 문헌에 보고된 현상
  이지만, `LiveNormalizer` 콜드스타트 시 좌표가 폭발하는 실제 버그도 있어
  고쳤고(§3과 같은 종류의 버그), 지터 완화 필터(One-Euro)와 시작 시 보정
  단계를 추가했다. §9 참고.

## 2. 데이터 누수 증명 (모델 학습 없이, `kslx.leak_report`)

```
python -m kslx.leak_report --root <004.수어영상 경로> --signers 1-16 --words 1-271
```

| 확인 항목 | 결과 |
|---|---|
| 같은 take의 5앵글 3D 키포인트 완전 동일 비율 | **100%** (30개 표본, max_abs_diff=0.0) |
| random 분할 val 클립 중 train에 같은 take(다른 앵글) 존재 | **100%** |
| take_out 분할 가능 여부 | 가능 (16 수어사로 확보) |
| signer_out 분할 가능 여부 | 가능 (16 수어사로 확보) |

### 독립 재확인 (`kslx.leak_report_npz`)

팀원이 별도 코드베이스로 미리 만들어둔 3D npz 캐시(`Dataset_NPZ/*.npz`, 이
저장소와 무관하게 "기본은 3D keypoint 사용"이라고 명시된 스크립트로 생성됨)로
같은 주장을 독립적으로 재확인했다:

- 표본 take 중 **92%**가 5개 "앵글" 샘플에서 3D 좌표가 완전 동일.
- 아주 단순한 1-NN 분류기로: **random 분할 72.0%** vs **take_out 분할 0.0%**.
  같은 데이터, 같은(=거의 없는) 모델로 분할 방식만 바꿔도 72%p 차이가 난다 —
  이게 순수하게 누수만으로 생기는 격차다.

## 3. 정규화 버그 (발견 및 수정)

`kslx/normalize.py`의 `center_and_scale`이 프레임마다 어깨너비로 좌표를
나누는데, 양쪽 어깨가 동시에 미검출(OpenPose 컨벤션상 (0,0,conf=0))된
프레임에서는 스케일이 0에 붕괴했다. 원래 코드는 이때 고정 최솟값(1e-3)으로
나눠서, 그 프레임의 다른(미검출과 무관한) 관절 좌표까지 **최대 약 100만 배**
폭발시켰다. 이 상태로 학습한 첫 결과는 모든 프로토콜에서 정확히
1/271(top1)·5/271(top5) — 즉 모델이 발산해서 아무것도 못 배운 순수 확률
수치에 멈춰 있었다.

수정: 스케일이 비정상적으로 작은(<5px) 프레임은 그 클립 안에서 정상 검출된
프레임들의 **중앙값 스케일**로 대체. 추가로 최종 피처에 [-20, 20] clip을
방어선으로 넣었다.

```
python -m kslx.train --data data/kslx/word_271.npz \
    --protocol random take_out angle_out signer_out --epochs 100 --tag base
```

| 프로토콜 | top1 | top5 | n_train | n_val | 의미 |
|---|---|---|---|---|---|
| random | 99.5% | 99.9% | 18,428 | 3,252 | 참고용 — 100% take 누수 |
| take_out | 93.6% | 96.0% | 18,970 | 2,710 | 같은 signer/단어 조합 미학습 |
| angle_out | 96.0% | 99.6% | 13,008 | 8,672 | 시점 일반화 상한선 |
| **signer_out** | **98.5%** | 99.2% | 17,615 | 4,065 | **미학습 수어자 — 이전엔 측정 불가였던 지표** |

## 5. 강건성 평가 (증강 전) — 모델 선택은 top-1이 아니라 이걸로

```
python -m kslx.eval_robust --data data/kslx/word_271.npz \
    --ckpt runs/random_base.pt runs/take_out_base.pt runs/angle_out_base.pt runs/signer_out_base.pt \
    --protocol angle_out
```

| 변형 | random | take_out | angle_out | signer_out |
|---|---|---|---|---|
| clean | 99.9% | 99.2% | 96.0% | 98.9% |
| yaw±15° | -1.6 | -1.2 | **-11.3** | -0.8 |
| yaw±30° | -30.2 | -21.2 | **-49.6** | -23.1 |
| 회전±15° | -3.2 | -2.2 | **-9.1** | -3.6 |
| **손 결측** | **-85.4** | **-86.0** | **-81.7** | **-84.5** |
| 스케일±25% | -1.0 | -0.4 | -2.7 | -0.5 |

두 가지 발견:

1. **angle_out 모델이 각도 변형에 제일 약하다** — 학습 때 5앵글 중 F/D/R만 보고
   L/U를 아예 안 보기 때문에, 5앵글을 전부 본 다른 모델들보다 시점 변화에
   더 취약하다. angle_out top-1만 보고 모델을 고르면 정확히 틀린 선택을 하게 된다.
2. **손 결측에는 네 모델 다 동일하게 붕괴한다** (14%대) — 학습에 증강이 전혀
   없었기 때문. → §6.

## 7. 웹캠 실시간 검증

학습 데이터는 AI Hub 5카메라 원본(OpenPose 포맷)이고 웹캠은 MediaPipe를
쓰므로, `kslx/adapters/mediapipe_adapter.py`가 그 변환을 맡는다.

- **pose/hand 매핑**: 관절 대응이 명확해 신뢰도가 높다 (직접 인덱스 대응).
- **얼굴 34점 매핑**: MediaPipe 공식 얼굴 영역 상수(`FACEMESH_LEFT_EYE` 등,
  google-ai-edge/mediapipe 저장소에서 가져온 정확한 인덱스)에서 균등
  서브샘플링한 근사치다. 학습 시 얼굴 좌표(AI Hub dlib68 기반)와 완전히
  일치하지는 않는다 — **미검증**. 웹캠 인식이 이상하면 `--no-face`로 먼저
  비교할 것.

```bash
pip install torch opencv-python mediapipe pillow numpy

python -m kslx.realtime --ckpt runs/signer_out_aug.pt
```

기본은 `--mode auto`: `kslx/stream.py`의 `SegmentGate`가 양손 이동량(에너지)을
프레임마다 재서 "에너지가 시작 임계값을 넘으면 녹화 시작, 저에너지가
`end_hold` 프레임만큼 이어지면 그 단어가 끝난 것으로 보고 자동 예측"하는
식으로 매번 SPACE를 누르지 않아도 이어서 인식하게 했다. `--mode manual` 로
기존 SPACE 방식도 유지되고, 실행 중 `M` 키로 전환된다.

★ 이건 정식 학습된 경계 검출기가 아니라 휴리스틱이다(§11 참고). 카메라가
손을 순간적으로 놓치면 에너지가 잘못 떨어져 단어가 중간에 끊길 수 있다.
화면에 실시간 `energy` 값이 표시되니 그걸 보면서 `--start-energy`/
`--end-energy`/`--end-hold` 를 조정하거나, 안 맞으면 `--mode manual` 로
돌아갈 것.

조작: `SPACE`(manual: 녹화 시작/중지, auto: 현재 구간 강제 종료) | `M` 모드
전환 | `R` 취소 | `Q`/`ESC` 종료.

체크포인트(`runs/signer_out_aug.pt`)와 MediaPipe 모델 번들
(`kslx/mp_models/holistic_landmarker.task`)은 저장소에 이미 포함돼 있다 —
**클론 후 별도 다운로드 없이 바로 실행 가능하다.**

## 8. 단어 → 문장 (`kslx/sentence.py`)

### 배경 — 왜 단어를 그냥 나열하면 안 되는가

한국수어(KSL)는 한국어를 그대로 손으로 옮긴 게 아니라 독립적인 문법을 가진
언어다. 조사·어미로 문법관계를 표시하는 한국어(교착어)와 달리 KSL은
고립어에 가깝다 — 조사가 거의 없고('부터', '와/과' 정도만 존재), 주격/
목적격/관형격 조사가 없다. 기본 어순은 SOV지만 조사가 없어도 되니 어순이
더 자유롭고, 주제화로 어순이 바뀐다. 의문문 같은 문장 종류는 단어가 아니라
비수지 신호(눈썹, 고개 등)로 표시된다 — 실제로 AI Hub 문장(SEN) 라벨에도
"장애인복지카드" 한 단어짜리 형태소에 `"1형태소 의문사 없는 의문형"`
태그가 따로 붙어 있었다(단어 자체가 아니라 표정이 문장 종류를 정한다는 뜻).

즉 인식 결과는 "조사·어미 없는 핵심어 나열"이고, 이걸 문장으로 바꾸는 건
기계번역의 gloss-to-text 문제다. AI Hub SEN 데이터를 확인해보니 형태소(단어)
나열만 있고 대응하는 완성 문장 텍스트가 없어서, 이 프로젝트 데이터만으로
학습 기반 번역 모델을 만들 수는 없었다. LLM API를 매 문장마다 호출하는
방법도 있지만(품질은 더 좋다), 이번 구현은 **완전 오프라인·무료**를
우선해 품사 기반 규칙으로 접근했다.

### 방법

`kiwipiepy`(순수 오프라인 한국어 형태소 분석기)로 각 단어를 태깅한다.
우리 어휘는 AI Hub 사전형 표기라 `가다`→가(VV)+다(EF), `학교`→학교(NNG)
처럼 잘 분석된다.

- 문장의 마지막 용언(동사/형용사)을 술어로 삼는다 (KSL도 SOV 성향이라
  어순을 임의로 재배열하지 않아도 대체로 맞는다).
- 술어 앞 마지막 명사에 술어 종류에 맞는 조사를 붙인다: 형용사 앞은 '이/가',
  이동동사(가다/오다류) 앞은 '에'(단, 그 명사가 대명사(나/너/저)면 목적지가
  아니라 주어라고 보고 '는'을 쓴다 — "나 빨리 가다"가 "나에 빨리 가요"가
  되는 걸 막는다), 그 외 동사 앞은 '을/를'. 술어 앞에 명사가 둘 이상이면
  맨 앞 명사는 주제 조사 '은/는'.
- 술어가 아예 없으면(명사만 나열 — AI Hub SEN에도 이런 단문이 있다) 마지막
  명사에 서술격조사를 붙여 평서문으로 만든다.
- `가다`가 kiwi 사전에서 다른 뜻(예: `배우다`→배우(俳優,NNG)+이다)으로
  오분석돼도, 우리 어휘는 "다"로 끝나면 사실상 항상 동사/형용사이므로 이
  표기 규칙으로 강제 보정한다.
- 조사/어미의 정확한 이형태(받침 유무에 따른 은/는, 이/가, 을/를, 이에요/
  예요, 불규칙 활용인 슬프다→슬퍼요, 나+가→내가 등)는 전부 `kiwi.join()`이
  자동으로 처리한다 — 직접 받침을 검사하는 코드는 없다.

### 예시 (전부 실측)

| 인식된 단어 | 완성된 문장 |
|---|---|
| 나, 학교, 가다 | 나는 학교에 가요 |
| 음료수, 마시다 | 음료수를 마셔요 |
| 나, 슬프다 | 내가 슬퍼요 |
| 너, 사랑하다 | 너를 사랑해요 |
| 나, 빨리, 가다 | 나는 빨리 가요 |
| 나, 수어, 배우다 | 나는 수어를 배워요 |
| 오늘, 날씨, 좋다 | 오늘 날씨가 좋아요 |
| 장애인복지카드 (단어 하나) | 장애인복지카드에요 |
| 학교, 친구, 만나다 | 학교는 친구를 만나요 ← 부자연스러움(아래 참고) |

### 알려진 한계

- **연속 명사 중의성.** "학교 친구 만나다"는 의도가 "학교 친구(복합명사)를
  만나요"일 수도 "학교는(주제) 친구를 만나요"일 수도 있는데, 지금 규칙은
  항상 후자로 해석한다 — 격틀(동사가 어떤 조사를 요구하는지)이나 의미
  관계를 보지 않기 때문이다.
- **동사 격틀 미반영.** '만나다'처럼 '을/를' 대신 '와/과'가 더 자연스러운
  동사가 있어도 구분하지 않는다.
- **일부 단어 품사 오분석.** '저' 같은 단어는 kiwi가 대명사가 아니라
  감탄사(IC)로 분석해 조사가 안 붙을 수 있다 (개별 사례, 문장 이해에는
  지장 없음).
- **문장 종류(의문문 등) 미반영.** 실시간 인식은 손 모양만 보므로(얼굴
  비수지 신호로 표시되는 의문문 등을 반영하지 않음) 항상 평서문으로
  나온다. 얼굴 34점 특징을 이미 뽑고 있으니(§7의 얼굴 매핑 참고), 눈썹
  올림 등을 감지해 의문형으로 바꾸는 건 다음 단계로 시도해볼 만하다.
- **학습 없이 규칙만으로 동작** — 이 모듈은 kslx 학습 파이프라인과 무관하게
  독립적으로 잘 작동하며 추가 학습이 필요 없다. 다만 품질을 높이려면
  (2)AI Hub SEN의 실제 문장 텍스트를 별도로 확보해 seq2seq 모델을 학습하거나
  (2)LLM API 호출로 교체하는 방법이 있다 (사용자가 오프라인/무료를
  선택해 이번엔 보류).

## 9. 웹캠 단어 인식 품질 (도메인 갭)

노트북 웹캠으로 실측 테스트해보니 단어 인식이 signer_out 97.8~98.5%
수치만큼 좋지 않다는 피드백을 받았다. 원인을 찾아 조사했다.

### 이건 어느 정도 예상된 문제다 (문헌 근거)

수어인식 연구 문헌을 찾아보니: **"OpenPose를 MediaPipe Holistic로
단순 대체하면 인식 성능이 크게 떨어진다"**는 게 이미 보고된 현상이다.
이유도 명확하다 — **MediaPipe는 손이 통째로(21점 전부) 빠지는 이산적
실패 패턴**인 반면 **OpenPose는 개별 관절만 빠지는** 실패 패턴이라, 두
검출기의 "무엇이 왜 실패하는지"가 근본적으로 다르다. 게다가 MediaPipe는
"손이 다른 신체 부위와 겹칠 때"(수어에서 매우 흔한 상황 — 손이 얼굴/가슴
앞으로 지나가는 동작이 많다) 특히 약하다는 것도 보고돼 있다.

즉 학습 데이터(AI Hub, OpenPose 5카메라)와 배포 환경(노트북 웹캠,
MediaPipe)의 검출기 자체가 다른 이상, 어느 정도 성능 하락은 구조적으로
불가피하다 — 이건 로컬 README.md가 처음부터 "미검증"이라고 경고했던
지점이기도 하다(§4.2 "MediaPipe ↔ OpenPose 도메인 갭").

### 그래도 고칠 수 있는 부분은 고쳤다

코드를 다시 보니 실제 버그가 있었다:

1. **`LiveNormalizer` 콜드스타트 버그.** 스트림 시작 직후처럼 어깨너비
   스케일을 한 번도 못 얻었을 때, 예전 코드는 학습 때와 똑같이 고정
   최솟값(1e-3)으로 나눠서 **좌표를 최대 100만 배까지 폭발**시켰다
   (§3의 학습 버그와 정확히 같은 종류의 버그를 실시간 코드에 또 심어놨던
   것). 이 폭발한 값이 에너지 계산에 들어가면서 있지도 않은 단어 시작/
   끝을 잘못 감지하게 만들었을 가능성이 크다. **수정: 유효한 스케일을
   아직 못 얻었으면 그 프레임은 그냥 건너뛴다** (에너지 0으로 처리,
   폭발 없음).
2. **키포인트 지터 완화 필터 추가.** MediaPipe 키포인트는 OpenPose보다
   프레임간 흔들림(지터)이 크다는 게 문헌에 나온다. One-Euro 필터
   (Casiez et al. 2012 — 가만히 있을 땐 세게 누르고 빠르게 움직일 땐
   반응성을 유지하는 적응형 저역통과 필터, HCI/제스처 인식에서 널리
   쓰인다)를 키포인트에 앞단에서 적용해서(`kslx/stream.py`
   `OneEuroFilter`) 이 흔들림을 줄였다.
3. **시작 시 보정 단계 추가.** 콜드스타트 버그가 다시 생기지 않도록,
   `realtime.py` 실행 시 어깨너비가 안정적으로 잡힐 때까지 기다렸다가
   본 인식을 시작한다.

### 지금 바로 시도해볼 수 있는 것

- 화면에 뜨는 `energy` 숫자를 보면서 조명이 밝은 곳에서 상반신(어깨 포함)이
  프레임 안에 다 들어오게, 카메라와 1~1.5m 거리를 두고 테스트해볼 것 —
  MediaPipe 자체가 조명/프레이밍에 민감하다.
- `--no-face` 로 얼굴 매핑(가장 미검증된 부분)을 꺼서 손/몸만으로 비교.
- `--min-cutoff`/`--beta` 로 스무딩 세기 조절 (값이 작을수록 부드럽지만
  반응이 느려짐).

### 근본적으로 더 고치려면 (다음 단계)

문헌에 따르면 **분류기의 마지막 레이어만 타깃 도메인(여기선 MediaPipe
웹캠 데이터)으로 파인튜닝해도 경쟁력 있는 성능이 나온다**고 한다. 즉
사용자가 웹캠으로 단어별 샘플을 몇 개씩(예: 10~20개) 녹화해서 라벨을
붙여주면, 그 데이터로 분류기를 파인튜닝해 실제 배포 환경에 맞출 수 있다
— 지금 당장 할 수 있는 것 중 가장 효과가 클 방법이지만 사용자의 데이터
녹화가 필요해서 이번 세션에서는 진행하지 않았다.

## 10. 271 → 1200단어 확장

동사가 271단어 안에 7개뿐이어서("배우다"조차 데이터셋에 없다는 걸 확인하며
발견됨) 실용적인 문장을 만들기 어려웠다. AI Hub 3000단어 전체가 이미
디스크에 있으니 새로 녹화할 필요 없이 범위만 넓히면 됐다.

### 3000단어 전체 시도 — 실패 (RAM 부족으로 강제종료)

16signer × 3000단어 × 5앵글 = 240,000클립을 전부 빌드하면 피처 배열 하나가
21.9GB — 이 PC 램(31GB)으로는 위험한 크기다. 처음엔 압축 없는 단일
`.npy`를 통째로 memmap 으로 열어 쓰는 방식으로 빌드했는데, **Windows 가
20GB 파일에 쓰기 작업을 하는 동안 더티 페이지를 계속 캐시에 쌓아서 실제로
시스템에 의해 강제종료됐다.** 해결책: 메모리맵을 계속 열어두는 대신 일반
파일 쓰기 + 주기적 flush/fsync 로 디스크에 그때그때 내려보내는 방식으로
바꿔서 빌드는 성공했다(240,000/240,000, 에러 0개, ~82분).

그런데 **학습 단계에서 같은 종류의 문제가 또 발생했다.** 검증셋 수만 개를
뒤섞인 순서로 memmap 에서 한 번에 읽는 게 사실상 20GB 파일 전체를
무작위로 훑는 것과 같아서 free memory 가 급락했다 — 자체적으로 감지해서
멈췄지만, 다시 시도했을 때도(학습 배치까지 포함해 한 epoch 이 결국 학습셋
전체를 훑는 구조라) 비슷한 패턴이 나타났다. `kslx/train.py`를 이렇게
고쳤다:

- 검증도 학습 배치처럼 memmap 에서 그때그때 청크 단위로만 읽는다 (한
  번에 다 안 올림).
- 읽기 전에 인덱스를 **global(X 전체 기준) 기준으로 정렬**해서 memmap
  접근이 순차에 가깝게 되도록 한다 (뒤섞인 순서로 몇만 개를 읽으면
  실질적으로 파일 전체를 무작위로 훑는 것과 같다).
- `--max-classes` 옵션 추가 — 앞에서부터 K개 클래스만 써서 한 epoch 이
  실제로 건드리는 총 바이트 수 자체를 줄인다. (`kslx.data.aihub`의
  `classes` 배열이 항상 오름차순 word id라, 앞 K개만 쓰는 건 재매핑 없이
  `y < K` 필터링만으로 된다.)
- `kslx/eval_robust.py`도 같은 문제(검증셋 통째로 GPU에 올려 강건성 평가
  중 **CUDA out of memory**까지 실측됨)라 청크 단위 forward + 동일한
  `--max-classes` 필터링을 추가했다.

이 과정에서 메모리를 몇 차례 직접 재보면서(`wmic OS get FreePhysicalMemory`)
플래토(안정화 지점)를 확인했다 — 데이터 크기에 거의 비례해서 free memory
가 줄다가 멈추는 패턴을 확인하고 나서야 어느 규모가 안전한지 판단할 수
있었다.

### 최종: 1200단어(96,000클립, ~8.7GB)로 안전하게 학습

기존 271단어의 4.4배. 메모리가 ~7GB 선에서 안정되는 걸 확인하고 4개
프로토콜(random/take_out/angle_out/signer_out, 50epoch, 증강 포함)을
전부 돌렸다 — 총 약 98분.

| 프로토콜 | top1 | top5 | n_train | n_val |
|---|---|---|---|---|
| random | 99.0% | 99.5% | 81,600 | 14,400 |
| take_out | 96.4% | 98.3% | 84,000 | 12,000 |
| angle_out | 95.0% | 98.5% | 57,600 | 38,400 |
| **signer_out** | **98.0%** | 99.4% | 78,000 | 18,000 |

271단어(signer_out 97.8%)와 사실상 동일하다 — **어휘를 4.4배 늘려도
미학습 수어자 정확도가 떨어지지 않았다.**

강건성도 확인했다(`eval_robust`, angle_out 검증셋 기준):

| 변형 | signer_out(1200) | angle_out(1200) |
|---|---|---|
| clean | 99.6% | 95.0% |
| yaw±30° | 99.4% (-0.2) | 93.1% (-1.9) |
| 손 결측 | 98.2% (-1.4) | 87.9% (-7.1) |

271단어 버전과 같은 패턴 — signer_out(5앵글 전부 학습)이 angle_out(3앵글만
학습)보다 훨씬 강건하다. **`runs/signer_out_c1200_aug.pt`를 새 기본
추천 체크포인트로 바꿨다** — 1200단어(`VOCAB_1200.txt`, 동사 121개 포함,
`가다/좋다/오다/아프다/예쁘다` 등)를 인식하고 정확도·강건성 모두 271단어
버전과 동급이다.

3000단어 전체는 이 PC RAM으로는 여전히 위험하다고 판단해 보류했다 —
더 큰 RAM이나 셰이딩(shard) 기반 학습 루프로 다시 시도해볼 수 있다.
